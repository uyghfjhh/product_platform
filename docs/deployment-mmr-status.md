# 部署页面 MMR 状态

默认展示 `node1 ACTIVE`、`node2 ACTIVE` 等诊断实际状态，不把 ACTIVE 翻译成“正常”。
ACTIVE 与 ERR_SUB_RUN 等诊断错误可以同时存在，异常摘要始终保留文本。

## 页面

- 拓扑下方以小字号“MMR 双活 · 组名”为标题，精简表格展示 MMR 节点、当前实例名、真实状态、问题；表格不显示端口。
- 点击表格行、“MMR 状态”按钮或连线标签，打开诊断抽屉；地址和端口只在详情／原始证据中显示。
- MMR 使用两条紫色独立连线，每条一个箭头，方向相反；物理流复制使用蓝色单向箭头，由当前主库指向备库。
- 箭头和动画仅示意复制方向，不表示已经检测到数据流或分别验证过双向复制健康。页面不额外放置常驻颜色图例，表格使用紧凑行高和 12px 正文，保持拓扑为视觉重点。
- 异常保留复制类型颜色，通过警示标签和文字摘要提示；不可达时降低亮度，仍可区分复制类型。
- 节点卡片及组标题不重复显示成员小字。MMR 物理备库不计为额外逻辑成员。
- 抽屉默认仅显示成员、状态、问题。展开某成员查看全部错误码、原始 detail 和各条观测来源。
- “诊断 SQL 与原始结果”默认折叠，保存实际执行的 SQL、返回值、错误、来源实例和耗时。
- 页面可见时每 30 秒采集，现有“刷新状态”及抽屉“重新检查”支持手动采集。
- 请求失败或结果超过 60 秒会标注过期/未知，不把历史结果当成当前状态。

## 后端

`GET /api/v1/environments/{environment_id}/mmr-status` 根据平台已登记配置选取实例和数据库。
每组先核对物理实例的 `pg_is_in_recovery()` 和当前数据库 `pg_extension`。
仅唯一、实际可写的主库可执行 MMR UDF，不向物理备库执行订阅运行诊断。
角色记录可能滞后，采集使用实际查询结果；没有主库或检测到双主时不任选一个冒充可信来源。
诊断 SQL 还在执行时重新判断 recovery，避免角色在采集期间变化。

元数据读取本地成员和 `fdd.mmr_node`，ACTIVE 本地主库执行 `fdd.show_node_info(true,false)`。
本地未初始化、非 ACTIVE 的加入/退出阶段分别报告限制。仅有元数据时明确显示“登记”，不伪造 real_nodestate。
从各主库采集完整列表，保留成员的每一条异常及 observer；界面计数按成员/错误码/detail 去重。
不同来源实际状态不一致、未取得本地来源、超时、权限错误、未知实际状态均单独报告，不宣称健康。

所有 SQL 为只读诊断，不自动变更发布、订阅、成员地址、内部状态或业务表。
数据库连接超时为 2 秒，每条 SQL statement_timeout=5秒、lock_timeout=1秒，环境级采集上限25秒。
数据库扩展按当前部署目标声明的数据库检查；不跨全部数据库自动安装或探测插件。

## 验证

- `tests/test_mmr_status.py`：角色记录滞后、物理备库不执行UDF、多异常来源、主库不可达、双主、加入中、未初始化、来源状态不一致及API。
- `frontend/tests/mmr-status.mjs`：真实实例展示和点击展开；模拟多异常及超时旧结果，不变更真实数据库。
- 本机四节点环境采集到 node1/node2 ACTIVE，来源为当前主 pg_1:16432、pg_2:26432，没有在 pg_3/pg_4 上调用 UDF。
