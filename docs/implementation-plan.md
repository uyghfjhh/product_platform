# 实施路线与需求核对

## 1. 本次交付边界

本阶段已开始实现独立平台。总体架构、开源选型、语言与部署方案、接口契约、前端和测试动画设计已落盘；Python 后端、React 页面、SQLite 任务、pgcluster 部署适配、License 生成和 fbasecman 报告入口已实现。准确的实现状态见 [实现进度](progress.md)。

这里的“设计覆盖”只表示已有明确方案和边界；真实部署和用例验收仍以进度文档中的命令与结果为准。

## 2. 用户要求逐项核对

| 用户要求 | 设计落点 | 实施时的直接证明 |
| --- | --- | --- |
| 面向公司所有产品的公共平台 | 产品目录、可选能力、通用工作台 | 接入第二个产品不改核心与共享页面 |
| 从零设计，不受旧测试框架限制 | 独立目录、新 SDK、pytest 内核、提供者接口 | 新应用运行不依赖旧测试框架的 import 路径 |
| 使用行业成熟开源框架 | React/Ant Design、FastAPI、Huey、pytest、Monaco、React Flow 等的选型表 | 锁定依赖，验证组件实际互通和可离线交付 |
| 架构整洁、清晰、可扩展 | 模块拥有自身数据，通过 contracts/服务接口协作 | 依赖检查和产品插件契约测试 |
| Python 等高级语言重写 License | Python 生成模块与成熟密码库 | 无 C 生成程序依赖，已发布产品能验签 |
| License 只要生成，不移植后台服务 | 同步生成下载 API，无申请表/签发队列 | 停止平台 Worker 后仍可使用生成接口 |
| 暂不部署数据库服务与 Redis | SQLite 与本地文件、SqliteHuey | 仅 Python 环境与发布包能启动，无额外数据库进程 |
| 内部使用，减少安全复杂度 | 同一内部信任域，基本参数与目标检查 | 首次使用不需要 SSO/多租户/审批配置 |
| 不需要测试 run_id | 固定当前结果键，短期调度引用 | 重跑覆盖当前结果，无测试批次历史目录/页面 |
| 商务简洁清晰的前端 | Ant Design tokens、浅色、表格与稳定布局 | 浏览器按页面和窄屏验收，无装饰性复杂动效 |
| 图形化数据库部署管理 | 拓扑模型、表单/YAML、无副作用计划、执行观察 | 在隔离环境实际部署并核对结果 |
| 数据库管理功能 | SQL、对象、会话、锁、参数、复制 | 单次 SQL 只执行一次，查询取消真实有效 |
| 自动化测试 | pytest SDK、资源 fixture、步骤与判定 | 真实 PASS/FAIL/BLOCKED/清理失败均正确 |
| 压测 | pgbench/JDBC/可选 Locust 提供者 | 正式负载有真实指标、阈值与收尾证据 |
| 稳定性测试 | 长进程监管、采样、恢复与报告 | 正式时长结束或取消后完整收尾，控制面重启不重复启动 |
| 测试动画展示 | 事件 reducer、二维拓扑、步骤/日志联动 | 真实事件播放正确，暂停画面不停止测试 |
| 原始日志高亮、搜索过滤 | 文件窗口、级别/节点/文本查询、原文定位 | 大日志与轮转测试，搜索不改原文 |
| 原始配置与语法高亮 | Monaco、原文快照、语言扩展、差异检查 | 配置展示完整，编辑检测并发修改与生效方式 |
| 自动化失败 AI 诊断 | 规则/检索/模型、引用与未知项 | 已知故障评估和证据准确性核对 |
| 知识库 | 文件与本地元信息、产品/版本检索 | 文档更新后检索不会继续使用陈旧片段 |
| AI 代码分析与回答 | 源码 revision、符号/文本索引、按需编译语义 | 引用正确，宏/版本不明确时说明范围 |
| 按模板生成优质测试报告 | 结构化事实、模板、受限 AI 文字区域 | 报告与证据逐项一致，没有虚构步骤或结论 |
| 可接其他产品与多活/企业版 | 提供者复用、产品能力声明、测试包 | 两个不同产品组合实际验收 |

## 3. 实施先后顺序

### 阶段 1：可启动的公共底座

实现发布目录、配置、Python API、React 页面骨架、SQLite schema 迁移、产品/环境目录和本机任务。建立共享日志、配置、步骤组件。至少注册两个不同产品的示例声明验证扩展性。

完成标准：一次启动入口带起必要进程；无外部数据库/Redis；页面刷新可恢复当前任务；真实插件注册错误有可读说明。阶段验收不以演示产品能显示卡片代替实际执行验证。

### 阶段 2：部署与数据库闭环

先选一个真实产品和隔离环境，打通配置、计划、部署、节点状态、原始日志与 SQL 工作台。采用产品提供者实现，参考 pgcluster 的有效领域逻辑。

完成标准：配置与图形一致；计划无副作用；真实部署、查询与收尾可核对；目标冲突与错误配置不会修改错误环境。

### 阶段 3：Python License 最小生成

先整理旧文件与密钥格式，使用专用测试密钥建立对照向量；实现参数校验、Python 生成和下载。

完成标准：无需旧 C 生成程序或其后台服务；与既有产品验签互通；不需要数据库申请表、审批页或队列 Worker。没有真实产品验签证据时不能只凭 Python 自验就宣布兼容。

### 阶段 4：新测试 SDK 与二维动画

实现 pytest 平台插件与两类代表用例：一个数据库/多活用例和一个代理类用例。保持真实操作、断言和清理语义；把步骤、观测、检查、日志关联起来。

完成标准：PASS/FAIL/BLOCKED/ERROR/取消可区分；动画与真实事件一致；原始文件可定位；回放不重复执行命令；不同产品共享同一组件。

### 阶段 5：压测与稳定性

实现方案、负载准备、预热、执行、指标与收尾；验证长进程监管、环境互斥及控制面重启。

完成标准：正式时长的真实测试完成；指标不使用固定占位值；取消与崩溃后的结果可信。短联调只能验证流程，不能替代正式稳定性结论。

### 阶段 6：知识、代码和 AI 报告

先做产品资料和源码检索，再接模型问答、失败诊断与报告文案。简单文本检索足以起步，不预先引入向量数据库服务。报告的固定事实无需 AI 即可生成。

完成标准：有来源引用、版本正确、已知故障评估可复现；模型不可用时基本报告和原始证据仍可查看；结果覆盖后旧分析不会误挂。

## 4. 新平台应建立的测试层次

| 层次 | 验证对象 |
| --- | --- |
| 单元测试 | 状态转换、结果映射、配置解析、日志区间、模板必填规则 |
| 契约测试 | 产品提供者、事件、OpenAPI 客户端、协议版本 |
| 本机故障恢复测试 | SQLite/队列之间失败、重复消息、Worker 中断、取消、产物原子发布 |
| 浏览器交互测试 | 产品切换、任务进度、日志搜索、配置查看、动画回放、License 下载 |
| 产品真实测试 | 部署、数据库动作、验签、负载、断言及清理在真实目标中的行为 |

测试不能只检查按钮存在或 HTTP 200；必须检查其业务效果，例如“下载的 License 被目标产品接受”“暂停回放不改变真实任务状态”。

## 5. 设计交付的检查记录

设计核查以当前文件为准：本文需求表应在其他文档中找到明确方案；链接应有效；代码示例应能解析；旧的 C 后台签发、首版 Redis/外部数据库、复杂权限等方案不能继续作为当前必选项。

交互示意只使用标注的模拟数据，单独检查按钮、播放状态、失败跳转、日志过滤与窄屏布局。它验证设计表现，不证明真实测试动画或后端已经完成。

后续实施时，每个阶段记录实际版本、环境、执行命令与结果。当前没有应用实现的验收记录，不把既有自动化框架的单测结果当成新平台的测试结果。
