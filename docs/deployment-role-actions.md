# 物理主备角色操作

操作对象是节点所在的 streaming 复制组；升主必须明确选择正在运行的实际备库。
前端确认框列出复制组、当前主库与地址、选中节点与地址及会被替换的数据目录。

| 动作 | 实际执行 |
| --- | --- |
| 备库升主 | 校验目标和 WAL 回放，停止旧主，提升选中备库，登记新主；旧主保持停止 |
| 主备切换 | 完成升主，让其余备库跟随新主，再重建旧主并验证 streaming 复制 |
| 重建旧主为备库 | 只处理记录中的旧主，使用当前主库备份替换其数据目录并验证复制；不再次升主 |
| 切回原主库 | 原主库必须已恢复为在线备库；将它提升，重建本次切换前的主库为备库 |

这四个 Web 动作通过平台 role_change.py 执行，不再让旧的 pgcluster failover 自行选择唯一备库。
请求必须携带 selected_node 和 expected_primary，目标为 streaming.<group>。
提交和执行前均重新核对实际角色，不自动替换目标；旧主无法确认停止时禁止升主。
允许旧主已确认停止的故障场景，但不能从其查询最终 WAL 位置，不承诺零数据丢失。
同环境有活动任务时拒绝新的角色操作；角色操作进行中拒绝其他部署动作。
引擎配置锁覆盖完整角色流程。

## 进度与恢复

任务持久化各阶段的 ROLE_PLAN / ROLE_STEP 事件；终端自动展开并显示待执行、执行中、通过和失败。
同时流式输出实际命令（含 psql SQL）、stdout/stderr、退出码和 pg_basebackup 进度。
日志对连接 password 字段脱敏。刷新页面可恢复当前环境保存的角色任务。
切换后的拓扑按实际 pg_is_in_recovery() 和受管角色记录刷新，而非固定展示配置中的原主。

新主确认后先写入角色状态，再进行旧主重建。失败不会把已经升主的节点伪装回旧状态。
重建前保存旧主主机、目录和备份来源的受管恢复记录；部分克隆失败时，仅该记录匹配且无 postmaster.pid 才允许恢复重建。
不会对未知目录执行自动认领或重建。完成复制验证后清理恢复记录。
多个备库中，其余备库先切上游，再重建旧主，避免重建的检查点先回收其所需 WAL。
已有备库严重滞后、所需 WAL 已丢失时，操作报出具体节点，不擅自删除并重建其他备库。

MMR 配置关联时额外执行 MMR 健康检查；没有修改 fbasecman 配置，不把物理升主等同于代理路由验收。

## MMR 切换前后适配

正常计划内切换先执行 MMR 健康检查；存在待处理发布变更、表结构不一致等错误时，在停止旧主之前终止。
旧主已确认停止的故障场景无法完成该前置检查，日志明确记录此限制，升主后仍需更新连接及复检。
升主登记后增加“同步MMR成员连接”阶段：通过 `fdd.alter_node_interface(..., false)` 在各当前可写成员更新被切换成员的 DSN 及相关订阅。
只接受匹配确认旧主或已经匹配新主的端点，不改写未知端点；既有认证参数由服务器内部读取并保留。
最终 MMR 健康检查允许最多 30 秒等待订阅工作进程重连，不把永久错误直接忽略。
不会通过强制把 `fdd.mmr_local_node.set_mode` 改为 d 来掩盖未完成的业务表发布。
